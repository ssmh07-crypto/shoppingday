# 다음 Codex 세션 인수인계

마지막 갱신: 2026-08-03 (KST)

이 문서는 대화 세션이 종료되거나 Codespace가 재시작된 뒤 작업을 이어가기 위한 기준 문서다. 인증정보와 Secret 값은 절대 이 문서에 기록하지 않는다.

## 2026-08-03 작업 중 인수인계

### 직감 전체 상품 가져오기

- 사용자는 API와 엑셀 내보내기가 없는 `zicgam.com`의 전체 상품을 가져오기로 결정했다.
- Chrome 확장 프로그램을 0.4.4로 올리고 `위탁상품 가져오기` 화면에
  `직감 전체 상품 가져오기`를 추가했다.
- 확장 프로그램은 로그인된 직감 승인 계정으로 홈의 전체상품 링크와 그 목록 페이지를 탐색해
  `product_no` 기준 상품 상세 주소를 중복 제거한 뒤 한 건씩 처리한다.
- 상품명, 공급가, 대표·상세 이미지, 상세 HTML, 옵션, 판매·품절 상태를 추출한다.
  한 상품을 Shoppingday API가 저장한 뒤에만 다음 상품으로 진행하며 요청 간 800ms,
  목록 탐색 간 400ms 간격을 둔다.
- 신규 직감 상품은 기존 공급처 상품과 판매 초안을 만들고, 재실행 시 기존 판매 편집값은
  보존하면서 공급처 원본만 갱신한다. 직감 공급처 레코드는 첫 저장 요청에서 멱등 생성해
  별도 migration은 없다.
- 진행률, 신규·갱신·변경 없음·실패 수, 중단 기능을 제공한다. 중단 후 재실행하면 목록은
  다시 탐색하지만 `product_no` 유일성으로 상품이 중복 생성되지 않는다.
- 전체 가져오기는 스마트스토어 자동 등록을 실행하지 않는다. 사용자가 가져온 상품 중
  등록할 상품을 별도로 검토한다.
- 파서 단위 테스트는 Cafe24 계열 목록·상세 fixture로 검증했다. 현재 Codex 세션에는
  연결 가능한 브라우저가 없어 실제 승인 계정의 목록·상세 DOM과 전체 상품 수는 확인하지
  못했다. 첫 실사용에서 목록 발견 수, 공급가, 이미지, 옵션을 반드시 표본 확인한다.
- 첫 실사용에서 직감 표시 전체 상품은 1,999개였지만 기존 0.4.0 수집기가 목록 150페이지에서
  2,477개를 발견했다. 상품 목록 밖의 추천·최근 본 상품 링크까지 읽은 것이 원인이므로
  0.4.1에서 `.prdList` 등 실제 목록 상품 영역과 페이지네이션만 읽도록 좁혔다.
- 상품 수는 신규·단종에 따라 변하므로 고정값이나 사용자 입력값과 일치하도록 강제하지
  않는다. 매 실행마다 현재 목록에서 발견한 상품 수를 표시하고 사용자가 확인한 뒤에만
  상세 조회와 DB 저장을 시작한다.
- 0.4.2에서도 모든 카테고리를 각각 순회해 108페이지와 2,122개 상품을 발견했다.
  0.4.3부터 홈의 `전체상품` 링크 하나만 선택하고
  그 목록의 페이지네이션만 순회한다. 링크를 찾지 못하면 다른 카테고리를 합산하지 않고
  중단한다.
- 공개 홈 HTML에서 실제 전체상품 링크가 `/product/list.html?cate_no=56`임을 확인했다.
  전체상품 목록 자체는 승인회원 전용이라 비로그인 HTTP 요청은 로그인 안내로
  전환된다.
- 0.4.4부터 페이지 수를 가정하지 않는다. URL 페이지 번호와 페이지네이션 활성 번호가
  일치해야 하고 같은 전체상품 목록의 `현재 + 1` 링크만 순차 탐색한다. 다음 번호가 없는
  활성 페이지를 마지막으로 판정한다.
- 번호 건너뜀, URL·상품번호 반복, 빈 목록, 로그인 전환, 탐색 중 표시 총수 변경은
  오류로 중단한다. 최종 고유 `product_no` 수와 사이트 표시 전체 수가 정확히 일치해야
  상세 저장을 시작하며 표시 총수를 읽지 못해도 중단한다.
- 로그인된 상세 페이지의 일반 승인회원 안내 문구를 로그아웃으로 오인하지 않도록,
  로그인 URL 또는 로그인 폼과 상품 상세 영역 부재를 함께 확인하도록 수정했다.

### Worker CPU·클라이언트 번들 최적화

- Cloudflare Worker에서 `Error 1102 Worker exceeded resource limits`가 발생했다.
- 관리자 전역 CSS를 상품 운영, 소싱, 도매사이트 메모 화면 단위 CSS로 분리하고
  클라이언트 번들 예산 확인 스크립트를 보강했다.
- `/admin/products`의 서버 조회와 클라이언트 목록 UI를 분리해 Worker가 한 요청에서
  처리하는 모듈과 직렬화 범위를 줄였다.
- 관리자 인증 경로는 Worker 내부에서 신뢰 헤더를 재사용하되 외부 요청이 같은 헤더를
  위조하지 못하도록 middleware에서 제거·재설정한다.
- 상품등록관리의 위탁상품은 약 6,173개를 한 번에 렌더링하지 않고 페이지당 100개만
  조회한다. 목록 진입 시 네이버 API를 호출하지 않으며 실제 작업 버튼을 누를 때만
  발행 상태를 검사한다.
- 위 최적화 후 사용자가 운영 사이트 접속 복구를 확인했다. 이후 대량 목록 기능도
  같은 원칙으로 서버 pagination과 요청형 외부 API 호출을 유지한다.

### 상품등록관리·위탁상품관리 통합

- 기존 `상품 관리` 명칭을 `위탁상품관리`로 변경했다.
- `/admin/registration`은 `소싱조사 상품`과 `위탁상품` 탭으로 분리했다.
- 위탁상품 탭은 공급처별 그룹과 공급처 필터를 제공하고 100개 단위로 페이지를
  이동한다.
- 소싱조사 및 위탁상품 행에서 네이버 `등록/변경`, `품절/판매재개`, `삭제`를 빠르게
  실행할 수 있다. 실제 네이버 변경은 확인창을 거쳐 요청한다.
- 소싱 등록 상품이 이미 발행된 경우 스마트스토어 등록 완료 상태, 채널상품번호와
  실제 등록 판매가를 목록에 표시한다.
- `/admin/wholesale-sites`에 도매사이트 링크, 이름, 설명을 추가·수정·삭제하고 새
  탭에서 여는 간단한 메모 페이지를 추가했다. 저장 테이블은
  `wholesale_site_links`, migration은 `0027_needy_maximus.sql`이다.

### 스마트스토어 역동기화·할인·태그

- 등록된 상품 편집 화면의 `스마트스토어 정보 불러오기`는 판매자센터에서 직접 바꾼
  상품명, 판매가, 즉시 할인율, 카테고리, 검색 태그와 공식 상품 속성을 Shoppingday
  편집 데이터로 역동기화한다.
- 역동기화는 배송 정책, 상세설명, 이미지, 옵션을 덮어쓰지 않는다. 원격 재고는 결과
  안내에만 표시하며 현재 로컬 재고 필드에는 저장하지 않는다.
- 저장하지 않은 로컬 편집값이 있으면 역동기화를 막아 덮어쓰기를 방지한다.
- 네이버 판매 정책에 `즉시 할인율`을 추가했다. 예상 할인가를 화면에 표시하고
  등록·수정 payload의 `customerBenefit.immediateDiscountPolicy`로 전송한다.
- 검색 태그는 네이버 추천 태그 API에서 동일 문구의 공식 태그 코드를 찾아
  `{code, text}`로 전송한다. 태그사전에 있는 단어가 코드 없는 사용자 태그처럼
  등록되던 문제를 수정했다.

### 범위형 사이즈 속성

- 욕실화처럼 범위형 사이즈 속성에 후보 구간과 정확한 실제값이 모두 필요한 경우,
  `사이즈 구간` 드롭다운과 `사이즈 실제값`, 단위를 함께 표시한다.
- 등록 준비 판정과 서버 검증에서도 필수 범위형 속성은 구간
  `attributeValueSeq`와 실제값을 모두 요구한다.
- 네이버 payload에는 선택 구간과 `attributeRealValue`를 함께 전송하며, 실제값은
  단위 코드가 없는 경우에도 누락하지 않는다.
- 스마트스토어에서 역동기화한 실제 사이즈도 같은 편집 구조의 실제값으로 보존한다.

### 성장상품관리 최신 기능

- 성장관리 상품을 `성장관리에서 제외`할 수 있다. 이 동작은 성장관리 연결과 분석·순위
  이력만 제거하며 상품 등록관리의 상품과 스마트스토어 상품은 유지한다.
- 성장상품관리에서 상품명·판매가·재고·판매 상태·검색 태그·네이버 속성을 변경해
  스마트스토어에 반영하면, 연결된 상품 등록관리 편집 데이터도 같은 값으로 동기화한다.
- 최근 7일·30일 판매 수량은 사용자가 새로고침할 때만 네이버 주문 API로 조회한다.
  중계 호출은 구간별로 속도를 조절하며 자동 주기 조회나 추정값은 만들지 않는다.
- 순위 이력 화면에 현재 상품명에 실제 포함된 키워드와 소싱 상품명 생성에 사용한
  키워드를 함께 표시한다. 키워드 칩을 누르면 바로 조회 키워드로 선택된다.
- 앞으로 소싱 상품명 초안을 만들 때 실제 사용된 `usedTitleKeywords`를
  `products.source_title_keywords`에 저장한다.
- 기존 상품에 저장값이 없으면 연결된 `sourcing_researches`의 소싱 키워드와 관련
  키워드로 동일한 기본 초안 규칙을 다시 실행해 복원 가능한 키워드를 표시한다.
  연결된 등록상품이나 소싱조사 기록이 없으면 복원할 수 없으며 빈 상태로 안내한다.

### 요청형 PC·모바일 순위 조회

- 사용자가 `PC·모바일 100위 조회` 버튼을 눌렀을 때만 로컬 네이버 API 중계 서버가
  Playwright와 시스템 Microsoft Edge를 실행한다. 예약·백그라운드 자동 조회는 없다.
- PC와 모바일 네이버쇼핑 공개 검색 화면을 각각 최대 100위까지만 확인한다.
- 결과는 `PC`와 `모바일`을 분리하고 `발견`, `100위 내 미노출`, `조회 차단`,
  `조회 실패` 상태로 저장한다.
- 이 값은 네이버 공식 순위 API 응답이 아니라 조회 시점의 공개 검색 화면 관측값이다.
  개인화·광고·검색 결과 변경에 따라 실제 사용자 노출과 다를 수 있다.
- CAPTCHA나 접근 제한 문구가 보이거나 상품 카드를 식별하지 못하면 잘못된 순위를
  만들지 않고 차단 또는 실패로 기록한다.
- 네이버 검색 화면 DOM은 연결 가능한 인앱 브라우저가 없어 실제 시각 검수하지 못했다.

  실제 검색 화면에서 다시 확인해야 한다.

### 최종 확정한 상품명 추천 규칙

1. 소싱 조사에서 사용자가 `상품명`으로 분류했고 실제 월 검색수가 1,000 이하인 관련
   후보 전체를 검토한다. 원산지·성능·착화감 등의 사실 여부는 추천기가 임의로
   추정하지 않고 사용자가 분류와 최종 편집에서 확인한다.
2. 같은 의미군에서는 사용자가 고른 기준 검색어, 기본 상품 유형과의 연결, 실제
   검색수, 구체성 순으로 대표 표현 하나를 고른다. 낮은 검색수의 긴 표현이 높은
   검색수의 관련 표현을 밀어내지 않는다.
3. `욕실화`, `욕실슬리퍼`, `화장실슬리퍼`, `욕실신발`은 욕실화 상품군의 동의
   상품형으로 연결한다. 실제 후보에 동의 상품형이 있으면 `수식어 + 명사` 기준점으로
   살려 수식어만 길게 나열하지 않는다.
4. 수식어가 많은 긴 제목은 기본 명사를 최대 두 번 배치하고 수식어 묶음의 표시
   길이가 비슷하도록 나눈다. 동일 명사 두 번은 네이버 공식 숫자 규정이 아니라
   Shoppingday 내부 가독성 기준이다.
5. 관련 후보 전체에서 최우선 키워드를 유지한 채 공백 포함 50자를 넘지 않는 조합 중
   제목 길이를 가장 충분히 활용한다. 기본 상품 유형이나 수식어를 중간에서 자르지
   않으며 40자 초과부터 내부 검토 경고를 표시한다.
6. 욕실화 실제 후보 39개로 재현한 최종 예시는 공백 포함 정확히 50자인
   `낮은 욕실화 안 미끄러운 푹신한 280 욕실화 앞막힌 EVA 물때 안 끼는 국산 욕실슬리퍼`
   이다. 설명용으로 나누면 `낮은 욕실화 / 안 미끄러운 푹신한 280 욕실화 /
   앞막힌 EVA 물때 안 끼는 국산 욕실슬리퍼`이며 화면에는 슬래시를 넣지 않는다.
7. `예쁜/이쁜`, 여러 미끄럼 방지 표현, 낮은 높이·문 걸림, 크기, `국산/국내산`은
   각각 같은 의미군으로 정리한다. `1+1`은 홍보성 표현으로 제거하고 `EVA`,
   `문에 안 걸리는`, `물때 안 끼는` 등은 읽기 좋은 표기로 보정한다.
8. 추천 결과에는 최종 제목에 실제 반영된 상품명 키워드와 검색수만 표시한다. 결과는

   남기고 `문에안걸리는` 같은 결합 표현은 읽기 좋은 띄어쓰기로 표시한다.

### 상품명 추천 현재 규칙

1. 소싱 조사에서 `상품명`으로 분류했고 월 검색수가 1,000 이하인 키워드만 상품명
   후보로 사용한다. 속성·태그·카테고리 분류값은 상품명에 넣지 않는다.
2. 사용자가 기준 상품명 검색어를 선택하면 해당 후보를 우선한다. 선택하지 않으면
   실제 검색수와 특징 다양성을 함께 고려한다.
3. 후보 전체는 선택 목록에 유지하고 관련 후보 전체를 의미군별로 정리해 조합에 검토한다.
4. 기본 상품 유형과 연결되지 않은 키워드, 홍보어, 넓은 일반 분류어, 정규화 중복을
   제외한다.
5. `낮은 높이·문 걸림`, `앞막힘`, `배수`, `빠른 건조`, `미끄럼 방지`, `착화감`,
   `무게`, `크기` 등의 의미군으로 후보를 나눈다. 같은 의미군에서는 사용자가 고른
   기준 검색어, 기본 상품 유형과의 연결, 실제 월 검색수, 구체성 순으로 대표 표현
   하나를 사용한다.
6. 포함 관계도 중복으로 처리한다. 예를 들어 `낮은욕실화`, `발등낮은욕실화`,
   `문에안걸리는 욕실화`가 함께 있고 별도 기준 검색어가 없다면 실제 월 검색수가
   가장 높은 관련 후보를 남긴다. 검색수가 같을 때 더 구체적인 표현을 고른다.
7. 수식어는 사람이 읽기 좋은 순서와 띄어쓰기로 정리한다. `욕실화`, `욕실슬리퍼`,
   `화장실슬리퍼`, `욕실신발`처럼 명확한 동의
   상품형은 욕실화 상품군 안에서 연결된 후보로 처리한다. 실제 후보에 서로 다른 동의
   상품형이 있으면 `낮은 욕실화 앞막힌 예쁜 안 미끄러운 국산 욕실슬리퍼`처럼
   `수식어 + 명사` 기준점을 앞과 끝에 두어 수식어만 길게 나열하지 않는다. 두 번째
   기준점은 후보에 있으면 `국산 욕실슬리퍼` 같은 자연스러운 원산지 결합을 우선한다.
   수식어가 많은 긴 제목에서는 동일한 기본 명사를 최대 두 번 배치해 중간 수식어
   묶음을 나눈다. 이 횟수는 네이버 공식 규정이 아니라 내부 가독성 기준이다.
8. 최종 추천은 50자를 넘지 않는다. 관련 후보 전체에서 최우선 키워드를 유지하면서
   50자를 넘지 않는 조합 중 제목 길이를 가장 충분히 활용한다. 기본 상품
   유형이나 수식어 중간을 잘라 길이를 맞추지 않으며 40자 초과부터 검토 경고를 표시한다.
9. 태그 후보는 검색수 제한 없이 전체를 추출하며 등록 편집에서 30자 이하 후보 중
   최대 20개를 사용자가 선택한다.

### 반드시 확인할 제한사항

- 외부 공급처 이미지 URL은 v2 상품 본문에 직접 사용할 수 없다. 반드시 네이버 이미지 업로드 API가 반환한 URL만 `storedUrl`로 사용한다.
- `product_publications`의 유일 제약, payload hash 비교, 상태 전이, 감사 로그, 관리자 상태 조회와 최종 확인 후 신규 등록 호출을 구현했다. 타임아웃·5xx 상태는 네이버 상품 목록과 대사하기 전까지 다시 등록하지 않는다.
- Quick Tunnel URL은 재실행할 때 바뀐다. `npm run naver:local-tunnel`이 Worker의 `NAVER_COMMERCE_RELAY_URL_OVERRIDE` Secret을 갱신한다.

배포 전에 dry-run 결과의 gzip 크기가 Cloudflare 무료 플랜 3 MiB 아래인지 확인한다.

## 2026-07-25 스마트스토어 등록 상품 관리

- 상품 편집의 스마트스토어 탭에서 이미 등록된 상품의 가격·이미지·상품명·상세·옵션 변경사항을 전체 수정 API로 반영할 수 있다.
- 판매 재개, 품절 처리, 판매 중지 버튼으로 원상품 판매 상태를 변경하고 `product_publications.remote_status_type`에 마지막 확인 상태를 저장한다.
- 네이버 상품 삭제는 오조작 방지를 위해 `삭제` 확인 문구를 요구한다. 채널 상품을 먼저 삭제하고 원상품을 삭제하며, 완료 후 로컬 발행 상태를 `deleted`로 기록한다.
- HMAC 중계 허용 목록에 원상품 수정·상태 변경·채널 상품 삭제·원상품 삭제 경로를 추가했다. 상품번호는 숫자만 허용하고 임의 경로 전달은 계속 차단한다.
- migration `0020_powerful_peter_quill.sql`은 원격 판매 상태 컬럼과 제약을 추가하며, 기존 발행 완료 상품은 `SALE`로 보정한다.

## 2026-07-25 성장 상품 관리 재설계

- `/admin/keywords`는 이미 등록된 스마트스토어 상품을 성장시키는 운영 화면으로 재정의했다.
- 상품 추가 시 연결 스마트스토어와 상품 링크를 선택하고 커머스 API에서 상품명·카테고리·속성·태그·대표 이미지·가격·재고·판매 상태를 가져온다.
- 상품명과 검색 태그 최대 10개를 편집한 뒤 사용자 확인을 거쳐 기존 원상품 전체 수정 API에 반영한다. 네이버 성공 응답 뒤에만 로컬 현재값을 갱신한다.
- 키워드 순위는 `keyword_rank_observations`에 사용자가 같은 조건에서 확인한 실제 순위와 확인일을 저장한다. 1,000위 안에서 찾지 못한 경우는 `rank = null`로 기록한다.
- 네이버 쇼핑 검색 Open API가 2026-07-31 종료 예정이므로 자동 순위 수집에는 연결하지 않았다. 지속 가능한 공식 공급원이 확인되면 현재 순위 이력 저장소에 별도 adapter를 연결한다.
- migration `0021_good_gargoyle.sql`을 적용했다. 기존 로컬 발행 상품과 연결된 성장 상품은 스토어 연결 ID를 자동 보정한다.
